# 덕르코프(ProjectD) 프로젝트 지침
 
> 작성일: 2026-10-09
 
## 1. 대화 방식
- 한국어, 존댓말, 간결하게 답한다
- 질문은 선택 버튼이 아니라 채팅 문장으로 한다
- 결정이 필요하면 선택지별 장단점과 추천을 먼저 설명하고, 최종 결정은 사용자가 내린다
- 확실하지 않은 내용(특히 Unity 6, Cinemachine 3, PUN 2 API)은 추측하지 않고 불확실하다고 밝힌다
## 2. 기준 문서
- GameDesign.md가 모든 기획 결정의 기준이고, WeekN_Checklist.md가 해당 주차 작업의 기준이다
- 요청이 기준 문서와 다르면 작업 전에 차이를 알려준다
- 현재 주차 범위 밖의 기능은 미리 만들지 않는다
- 문서는 수정안을 먼저 보여주고 허락을 받은 뒤 갱신한다 ("바로 반영"이라고 하면 즉시 갱신)
- 문서를 갱신하면 변경 이력에 날짜와 내용을 기록하고, claude.ai 프로젝트에도 저장한다
- 새 대화를 시작하면 해당 주차 체크리스트의 현재 위치와 "현재까지 만든 스크립트" 목록부터 확인한다
## 3. 코드 난이도
- 취업용 포트폴리오이므로 면접관이 바로 읽을 수 있는 코드를 목표로 한다. 짧은 코드보다 읽기 쉬운 코드를 우선한다
- 사용: 클래스, 인터페이스, C# 이벤트, 코루틴, ScriptableObject, Unity 기본 API
- 사용하지 않음: 외부 DI 프레임워크, UniTask와 async 남용, 리플렉션, 복잡한 제네릭, 여러 단계를 이은 LINQ, DOTS
- 더 어려운 방식이 꼭 필요하면 이유를 설명하고 허락을 받는다
## 4. 설계 원칙
- SOLID를 준수한다. 단, 인터페이스와 추상화는 실제로 교체되거나 구현이 여러 개일 때만 만든다
- 한 클래스는 한 가지 일만 한다. 한 파일에 한 클래스, 파일명은 클래스명과 같다. 단, 열거형은 Core/Define/Enum.cs 한 파일에 모은다
- 모듈 하나를 수정하거나 삭제해도 다른 모듈이 컴파일되고 동작해야 한다
- 같은 오브젝트 안은 직접 참조, 시스템 사이는 C# 이벤트로 통신한다. UI는 이벤트를 구독만 하고, 게임 로직은 UI를 모른다. 단, 매 프레임 바뀌는 값을 그리는 UI(조준점 등)는 읽기 전용 값을 매 프레임 읽을 수 있다
- 싱글톤은 세션, 저장, 네트워크에만 쓴다
- 입력과 동작을 분리하고, 로컬 플레이어 전용 처리는 한곳에 모으며, 발사는 발사 정보로 표현한다 (네트워크 대비)
- GameDesign.md 9-1 권한 표를 따른다
- 수치는 코드에 박지 않고 인스펙터 값이나 ScriptableObject로 둔다
## 5. 코드 작성 규칙
- 네임스페이스는 ProjectD.하위모듈 형식으로, Assets/_Scripts 아래 폴더 구조와 맞춘다
- 클래스, 메서드, 프로퍼티는 PascalCase, private 필드는 _camelCase로 쓴다
- 인스펙터에 노출할 값은 [SerializeField] private로 선언하고, public 필드는 쓰지 않는다
- Unity 6 기준 API를 쓴다 (구 Input 클래스 금지, Cinemachine 3 기준, FindObjectOfType 대신 FindFirstObjectByType)
- Update에서 GetComponent나 Find를 호출하지 않고, Awake에서 캐싱한다
- 같은 오브젝트의 참조는 TryGetComponent로 찾는다. 인스펙터 연결 값을 덮어쓰지 않도록 `if (_field == null && !TryGetComponent(out _field))` 형태로 쓰고, 실패하면 한글 경고를 출력한다. Try 버전이 없는 GetComponentInChildren, GetComponentInParent는 그대로 쓴다. 2026-11-06 이후 새로 만들거나 고치는 스크립트부터 적용하고, 기존 스크립트는 8주차에 통일한다
- 필수 참조가 비어 있으면 한글 경고 로그를 출력한다
- 애니메이터 파라미터, 셰이더 속성 등 문자열 이름은 Core/Define 폴더의 용도별 정적 클래스(AnimatorParams, ShaderPropertyIds 등)에 static readonly 해시/ID로 모으고, 코드에서는 문자열을 직접 쓰지 않는다
## 6. 주석 규칙
- 주석은 한글로 쓴다
- 주석 설명 문장에는 이모지와 특수기호를 쓰지 않는다
- 파일 첫 줄에 파일 경로를 주석으로 적는다. 예: // 파일 경로: Assets/_Scripts/Player/PlayerMover.cs
- 클래스 위에 역할을 설명하는 XML 주석을 단다
- private을 포함한 모든 함수 위에 XML 주석(summary)으로 하는 일을 적는다. 매개변수와 반환값이 있으면 param, returns도 적는다
- 계산이 복잡하거나 이유 설명이 필요한 줄에만 줄 주석을 단다
- 주석에 주차, 작업 항목 번호, 문서 섹션 번호, 앞으로의 작업 계획을 쓰지 않는다. 코드가 무엇을 왜 하는지만 쓴다. 2026-11-07 이후 새로 만들거나 고치는 스크립트부터 적용하고, 기존 스크립트는 8주차에 통일한다
## 7. 스크립트 제공 방식
- 사용자가 요청할 때만 작성한다
- .cs 파일로 제공한다. 파일이 두 개 이상이면 Assets/_Scripts 아래 폴더 구조대로 묶어 압축 파일 하나로 제공한다
- 파일마다 신규 파일인지 수정 파일인지와 저장 위치를 명시한다
- 수정 파일은 바뀌는 줄 수에 따라 제공 방식을 나눈다
  - 10줄 이상 수정: 전체 파일을 제공하고, 위에 바뀐 함수 목록을 요약한다
  - 10줄 미만 수정: 파일 이름, 함수 이름, 몇 번째 줄인지 알려주고 바뀐 부분만 제공한다
- 스크립트 뒤에 에디터 설정 방법(붙일 오브젝트, 인스펙터 연결 값)과 확인 방법을 안내한다
- 기존 스크립트를 수정할 때는 최신 내용을 먼저 확인한다. 확인할 수 없으면 사용자에게 파일 내용을 요청한다
- 새 스크립트를 만들거나 기존 스크립트의 공개 함수가 바뀌면 체크리스트의 "현재까지 만든 스크립트" 목록을 갱신한다
## 8. GitHub
- 커밋은 사용자가 요청할 때만 작성한다. 기능이 끝나도 커밋 여부를 묻지 않는다
- 요청을 받으면 마지막 커밋 이후의 모든 변경을 한 번에 정리해 Summary(영어)와 Description(한글)을 작성한다
- 변경이 여러 종류이면 Summary의 type은 가장 큰 변경 기준으로 정하고, 나머지는 Description에 정리한다
- 마지막 커밋 이후의 변경 내용은 체크리스트의 "커밋 대기 내용"에 계속 기록하고, 커밋 후 비운다
- 기능 커밋 형식
  - Summary: 영어, Conventional Commits 형식. type(scope): 내용 (예: feat(player): add dodge with invincibility frames)
  - type: feat(새 기능), fix(버그 수정), refactor(구조 개선), docs(문서), chore(설정·패키지·에셋), perf(성능)
  - scope: 스크립트 폴더 이름 소문자 (player, combat, ai, network, inventory, ui, core, data, world). 특정 모듈이 아니면 생략
  - 내용은 소문자로 시작하는 명령형, 마침표 없이, 50자 이내
  - Description: 한글로, 바뀐 내용을 짧은 목록으로 정리
- 주차 할 일이 모두 끝나면 마무리 커밋의 Summary와 Description을 작성하고, 태그 weekN을 붙인다
  - Summary: chore: complete week N - 주차 목표 (예: chore: complete week 1 - offline player prototype)
  - Description: 한글로 작성
