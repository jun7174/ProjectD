## 1. 4주차 목표
 
맵에서 **상자와 적 시체를 열어 아이템을 꺼내고, 그리드 인벤토리에 정리하고, 땅에 버리고 줍는** 파밍을 만든다. 상자 내용물과 줍기는 마스터가 결정하고, 모든 화면과 중도 참가자에게 같게 보인다. 함께 레이드 안 채팅을 넣는다.
 
완료되면 할 수 있어야 하는 것
- Tab으로 4×4 그리드 인벤토리를 열고, 아이템을 드래그로 옮기고, 드래그 중 R로 회전하고, 같은 아이템은 자동으로 합친다
- 상자에 다가가 F를 1초 누르면 열리고, 인벤토리 옆에 상자 그리드가 보이며, 드래그나 우클릭으로 꺼낼 수 있다
- 적을 죽이면 시체가 루팅 상자가 된다
- 두 명이 같은 상자를 동시에 열어도 아이템이 하나만 나간다 (마스터 승인)
- 아이템을 땅에 버리면 모든 화면에 보이고, 다른 사람이 주울 수 있다
- 나중에 들어온 사람에게도 상자 내용물, 꺼내진 아이템, 땅에 떨어진 아이템이 같게 보인다
- 마스터는 각 플레이어의 아이템 목록 사본을 가지고 있다
- Enter로 채팅을 열어 팀원에게 메시지를 보낼 수 있다
체크포인트 (GameDesign 13-1): **4주차 끝에 두 명이 함께 들어가 적을 잡고 아이템을 주울 수 있어야 한다**

## 2. 결정 사항
 
2026-11-19 사용자 결정: **I1~I11 모두 추천안으로 확정**
 
### I1. 아이템 데이터 구조와 ID [확정: A]
 
GameDesign 6번: 공통 ItemData를 무기, 탄약, 방어구, 소모품 데이터가 상속.
 
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. `ItemData` 하나를 부모로, `WeaponData`, `AmmoData`, `ConsumableData`가 상속. 방어구·가방·잡동사니·교환 재화·열쇠는 4주차에는 `ItemData` 그대로 쓰고 필요할 때 자식 클래스 추가. 데이터베이스는 `ItemDatabase` 하나로 합침 **추천** | 줍기·저장·전송이 모두 아이템 ID 하나로 통일. 실제로 동작이 다른 것만 자식 클래스 | WeaponData의 부모를 바꾸므로 기존 무기 에셋 값이 유지되는지 확인 필요 |
| B. ItemData와 WeaponData를 따로 두고 무기 아이템이 WeaponData를 참조 | 기존 WeaponData를 건드리지 않음 | 무기만 다른 경로를 타서 코드가 두 갈래가 됨 |
 
- A 추천 세부
  - ID 대역: 무기 1000번대(유지), 탄약 3000, 방어구 4000, 가방 5000, 소모품 6000, 잡동사니 7000, 교환 재화 8000, 열쇠 9000 (적 2000번대는 아이템이 아님)
  - `ItemData` 공통 필드: ID, 이름, 아이콘, 월드 프리팹, 그리드 크기(가로×세로), 최대 스택, 판매가, 희귀도(3단계), 분류. 분류와 희귀도는 `Enum.cs`의 `ItemCategory`, `ItemRarity`
  - WeaponData의 기존 이름 필드는 부모로 옮긴다. 필드 이름(`_displayName` 등)을 그대로 두면 에셋 값이 유지되는 것으로 알고 있으나, 옮긴 뒤 무기 에셋 3개의 값을 눈으로 확인한다 (확인 필요)
  - `WeaponDatabase`는 `ItemDatabase`로 교체하고, 무기가 필요한 곳(PlayerFireSync 등)은 `TryGetItem` 후 `WeaponData`인지 확인
### I2. 아이템을 들고 다니는 단위 [확정: A]
 
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 아이템 묶음 = (아이템 ID, 개수). 인벤토리 칸에는 묶음과 위치·회전을 두고, 네트워크와 마스터 사본에는 (ID, 개수)만 보냄 **추천** | 전송과 저장이 단순. 4주차 아이템에는 개별 상태(내구도 등)가 없음 | 나중에 아이템별 상태(무기 탄창 탄 수 등)가 생기면 필드 추가 필요 |
| B. 아이템마다 고유 번호를 붙여 추적 | 개별 상태와 추적이 쉬움 | 번호 발급·전송·검증이 늘어남 |
 
- 상자 안 아이템은 "상자의 몇 번째 칸(항목 번호)"으로 식별한다. 줍기 요청은 (상자, 항목 번호)
### I3. 그리드 인벤토리 UI 방식 [확정: A]
 
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. UGUI + EventSystem 드래그 인터페이스(IBeginDragHandler, IDragHandler, IEndDragHandler) **추천** | 자료가 많고 2주차 UI와 같은 방식. 칸 크기 고정(예: 64px)으로 계산이 단순 | 드래그 중 회전·스냅 처리를 직접 작성 |
| B. UI Toolkit | 최신 방식 | 학습 비용, 드래그 처리 자료가 적음 |
 
- 로직과 화면을 나눈다: 그리드 계산(배치 가능 여부, 빈 자리 찾기, 합치기)은 MonoBehaviour가 아닌 일반 클래스 `InventoryGrid`, 화면은 그것을 그리기만 함. 면접에서 설명하기 좋고 EditMode 테스트도 가능
### I4. 인벤토리를 연 동안의 조작 [확정: A]
 
GameDesign 6번: 인벤토리를 열어도 게임은 계속 진행, 이동 가능, 사격 불가.
 
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 이동·회피 가능, 사격·정밀 조준·재장전 불가, 캐릭터 방향은 연 순간 그대로 고정, 시스템 커서 표시·조준점 숨김 **추천** | 드래그하는 동안 캐릭터가 마우스를 따라 빙빙 돌지 않음. 위험하면 피할 수 있음 | 연 동안 뒤에서 오는 적을 보려면 닫아야 함 |
| B. 조준 방향도 계속 마우스를 따라감 | 구현이 단순 | 드래그할 때마다 캐릭터가 돌아 어색함 |
 
- 채팅 입력 중에는 모든 게임 입력(이동 포함)을 막는다 (GameDesign 9번)
- 입력 막기는 I10의 `PlayerInputGate` 하나로 처리
### I5. 상자 내용물 생성과 동기화 [확정: A]
 
GameDesign 6번, 9-4: 내용물은 레이드 시작 시 마스터가 정하고 상자 오브젝트에 동기화.
 
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 상자는 맵에 미리 배치한 씬 오브젝트(PhotonView). 마스터가 Start에서 루팅 테이블로 내용물을 정해 RPC로 모두에게 보내고, 꺼내질 때마다 "몇 번 항목이 빠짐"을 모두에게 보냄. 중도 참가자에게는 현재 내용물 전체를 한 번 보냄 **추천** | 모든 화면이 내용물을 알고 있어 열자마자 보임. 9-4(마스터 이전 대비)와 일치. 3주차 NetworkHealth와 같은 패턴 | 상자 30개 × 내용물을 시작 시 한 번에 보냄 (작은 양) |
| B. 상자를 열 때 마스터에게 내용물을 요청 | 안 여는 상자는 전송 없음 | 열 때 왕복 지연, 9-4와 맞지 않음 |
 
- A 추천 세부: 상자와 적 시체가 같은 컴포넌트를 쓴다. 내용물 목록(`LootContainer`, Inventory 모듈)과 동기화(`LootContainerSync`, Network 모듈)를 나눈다
- 씬 PhotonView는 씬에 미리 있으므로 중도 참가자도 같은 상자를 가진다 (확인 필요: 씬 오브젝트의 ViewID가 모든 클라이언트에서 같게 배정되는 것으로 알고 있음)
### I6. 줍기 승인 흐름 [확정: A]
 
GameDesign 9-1: 아이템 줍기는 RPC 요청 후 마스터 승인, 중복 획득 방지.
 
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 요청 전에 내 인벤토리에 자리를 먼저 확인·예약 → 마스터에 요청 → 마스터가 검증(항목이 아직 있는지, 거리) 후 모두에게 "빠짐" 알림 + 요청자에게 승인 → 요청자가 예약한 자리에 넣음. 거절이면 예약 해제 **추천** | 승인 후 자리가 없어서 생기는 문제가 없음. 두 명이 동시에 집어도 먼저 도착한 요청만 승인 | 예약 처리 코드가 필요 |
| B. 승인 후에 자리를 찾고, 없으면 땅에 떨어뜨림 | 예약 없음 | 승인됐는데 바닥에 떨어지는 어색함 |
 
- 묶음은 통째로만 꺼낸다 (일부만 꺼내기 없음). 자리가 없으면 요청하지 않고 "공간 부족" 표시
- 마스터 승인 시 그 플레이어의 아이템 목록 사본(I9)도 함께 갱신
### I7. 땅에 버린 아이템(월드 아이템) [확정: A]
 
GameDesign 6번: 팀원 간 교환은 땅에 버려서 주는 방식만. 월드 아이템은 네트워크 동기화, 풀링하지 않음.
 
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 버리면 마스터에게 요청 → 마스터가 `InstantiateRoomObject`로 월드 아이템 생성(생성 데이터: 아이템 ID, 개수). 줍기는 I6과 같은 승인 후 마스터가 `PhotonNetwork.Destroy` **추천** | 중도 참가자는 생성 정보로 자동으로 받고, Destroy된 것은 자동으로 빠짐. 3주차 적 생성과 같은 방식 | 버릴 때마다 네트워크 오브젝트 하나 (버리는 횟수가 적어 문제없음) |
| B. 월드 아이템 목록을 한 관리자 오브젝트가 들고 RPC로 동기화 | 네트워크 오브젝트가 늘지 않음 | 중도 참가 전송을 직접 작성 |
 
- 모양: 네트워크 프리팹은 공용 `WorldItem` 하나. 생성되면 각 화면이 ItemData의 월드 프리팹을 자식으로 붙여 모양을 만든다
- 버리는 방법: 인벤토리 창 밖으로 드래그해서 놓기
- 버릴 때 내 인벤토리에서는 바로 빼고 마스터 사본에서도 뺀다 (마스터는 사본에 그 아이템이 있는지 검증)
### I8. 상호작용(F) 방식 [확정: A]
 
GameDesign 2번: F 하나로 통합, 가장 가까운 대상 하나에 강조 표시, 우선순위 부활 > 상자 > 아이템. 줍기는 짧게, 상자 열기는 길게.
 
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 내 캐릭터의 `PlayerInteractor`가 0.1초마다 반경(약 2m) 안 Interactable 레이어에서 대상을 찾고, 우선순위 → 거리 순으로 하나 선택. 대상은 `IInteractable`(우선순위, 길게 누를 시간, 안내 문구, 실행) 구현. 화면에 "F 열기 / F 줍기" 안내와 길게 누르기 진행 막대, 대상은 색으로 강조 **추천** | 부활(7주차)도 같은 인터페이스로 추가. 구현이 여러 개라 인터페이스 기준에 맞음 | 외곽선 셰이더 같은 정식 강조는 7주차 |
| B. 트리거 콜라이더 출입으로 대상 관리 | 이벤트 방식 | 꺼진 오브젝트·여러 대상 처리 복잡 |
 
- 상자 내용물이 열려 있는 동안 멀어지면(예: 3m) 상자 창을 닫는다
### I9. 마스터의 아이템 목록 사본 [확정: A]
 
GameDesign 6번, 9-1: 마스터가 각 플레이어의 아이템 목록 사본을 보유 (끊김 시 시체 생성에 사용, 5주차).
 
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 마스터의 `PlayerItemLedger`(Network)가 플레이어 번호별로 (ID, 개수) 목록을 보관. 줍기 승인, 버리기 때만 갱신. 그리드 위치는 모름 **추천** | 그리드 이동은 전송 없음. 버리기 검증에 사용 | 5주차 아이템 사용(소모)과 출격 장비도 사본에 반영해야 함 |
| B. 클라이언트가 인벤토리가 바뀔 때마다 전체 목록을 마스터에 보냄 | 단순 | 클라이언트 말을 그대로 믿는 구조라 승인의 의미가 약해짐 |
 
- 확인용으로 마스터 화면에 사본을 보는 디버그 표시(컨텍스트 메뉴 로그)
### I10. 채팅 구현 [확정: A]
 
GameDesign 9번 채팅 규칙.
 
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. Raid 씬 오브젝트(PhotonView)의 `RaidChat`(Network)이 `RpcTarget.All`로 메시지를 보내고, 보낸 사람 이름은 받는 쪽에서 `info.Sender.NickName`으로 붙임. 화면은 `ChatView`(UI). 입력 중 게임 입력 막기는 내 캐릭터의 `PlayerInputGate`(Player)에 요청 **추천** | 이름을 위조할 수 없음. 입력 막기를 한 곳에 모아 인벤토리와 함께 사용. UI가 Player를 참조하는 것은 조준점(CrosshairView)과 같은 방향 | 바인더(내 캐릭터 생성 시 연결)가 하나 더 필요 |

### I11. 임시 아이콘과 아이템 목록 [확정: A]

## 5. 4주차 코드 원칙
 
1. **로직과 화면을 나눈다.** 그리드 계산은 일반 클래스(InventoryGrid)에 두고 UI는 그리기와 입력 전달만 한다
2. **아이템은 ID와 개수로 보낸다.** ScriptableObject는 보낼 수 없으므로 ItemDatabase로 찾는다 (2주차 무기 ID와 같은 방식)
3. **결과를 정하는 것은 마스터다.** 상자 내용물, 꺼내기, 버리기, 땅에서 줍기는 모두 마스터가 승인한다. 그리드 배치만 로컬
4. **한 번 일어난 일은 참가 시점에 보낸다.** 상자 내용물과 빠진 항목은 중도 참가자에게 마스터가 한 번 보낸다
5. **상자와 시체는 같은 코드를 쓴다.** 5주차 플레이어 시체도 같은 루팅 상자를 재사용한다
6. **Inventory 모듈은 Network를 모른다.** 네트워크 처리는 Network 모듈의 동기화 컴포넌트가 맡는다 (3주차 AI와 같은 방식)

## 8. 개발 일지 후보 (해결한 기술 문제)
 
4주차에 해결한 기술 문제를 여기에 기록하고 개발 일지에 옮긴다.
 
1. 동시 꺼내기 중복 방지: 요청자가 인벤토리 자리를 먼저 예약하고, 마스터는 먼저 도착한 요청만 승인한다. 나중 요청은 거절되어 예약이 풀리므로, 승인됐는데 자리가 없는 경우가 생기지 않는다
2. WeaponData의 부모 변경: ItemData를 상속하게 바꾸면서 `FormerlySerializedAs`로 기존 무기 에셋의 ID와 이름을 유지했다
3. 시체 상호작용 콜라이더: 꺼 둔 자식 오브젝트로 분리해, 죽을 때 EnemyDeath가 콜라이더를 끄는 처리와 섞이지 않게 했다
4. UI 구조: 화면 스크립트는 부모에 두고, 켜고 끄는 Root는 자식으로 분리했다. 스크립트가 붙은 오브젝트를 끄면 Update가 멈춰 Tab으로 다시 열 수 없기 때문이다
5. 알려진 문제: 묶음 나누기가 없어서, 드래그로 합치기는 가득 찬 묶음과 덜 찬 묶음 사이에서만 의미가 있다. 덜 찬 묶음끼리는 주울 때 이미 자동으로 합쳐진다
6. 설정 실수 기록: 아이템 에셋의 Max Stack 기본값이 1이라 개수가 표시되지 않고 합쳐지지 않았다. 탄약·소모품 에셋의 Max Stack을 지정해 해결
