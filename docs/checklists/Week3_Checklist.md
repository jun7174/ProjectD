## 1. 3주차 목표
 
맵 위에서 **적이 플레이어를 감지하고, 쫓고, 공격하는** 협동 전투를 만든다. 적 AI는 마스터에서만 실행하고, 다른 클라이언트는 결과(위치, 상태)만 받아 보여 준다.
 
완료되면 할 수 있어야 하는 것
- 건물 안에 들어가면 천장이 사라지고, 캐릭터를 가리는 벽은 반투명으로 보인다
- 공사장 맵에서 적이 순찰하다가 플레이어를 보거나 소리를 들으면 경계 게이지가 차고, 가득 차면 추적한다
- 몰래 지나가면(걷기, 시야 밖) 들키지 않고 지나갈 수 있다
- 돌격형은 예고 동작 후 돌진하고, 사수형은 거리를 유지하며 느린 탄을 점사한다
- 적의 공격에 맞으면 체력이 줄고, 회피 무적 구간에서는 맞지 않는다 (피격자 최종 확인)
- 인원에 따라 적 체력이 바뀌고, 중도 참가자에게도 적의 현재 상태가 같게 보인다
- 멀리 있는 적은 휴면해서 성능과 전송량을 아낀다

### F1. 천장 처리 방식 [확정: 숨김(그림자만 남김), 머리 위 레이로 감지]
 
- 2026-11-06 결정: 건물에 들어가면 그 건물 천장을 숨긴다(그림자만 남겨 실내 어둠 유지). 천장 반투명(B안)은 쓰지 않음
- 감지 방식 변경 (2026-11-06): 실내 트리거 대신 **내 캐릭터 머리 위로 레이를 쏴서** 덮고 있는 천장을 찾는다. 건물마다 트리거를 만들 필요가 없고, ㄱ자 건물도 그대로 동작하며, 꺼진 컴포넌트가 트리거 이벤트를 받는 문제도 없다. 천장에 콜라이더가 필요하다
### F2. 벽 반투명 구현 방식 [확정: 투명 머티리얼 교체]
 
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 가릴 때 투명 머티리얼로 교체 **추천** | 가장 단순함 | 투명끼리 겹치면 정렬이 어색할 수 있음 |
| B. 디더링 셰이더(Shader Graph) | 정렬 문제 없음, 보기 좋음 | 셰이더 작업 시간 필요 |

### F3. 벽과 천장을 같은 코드로 처리 [확정: A. 컴포넌트 하나 + 숨기는 방식 설정]

|---|---|---|

### E3. 적 네트워크 생성 방식 [확정: A. InstantiateRoomObject]
 
GameDesign 5번: 고정 스폰 지점 + 지점별 적 종류 랜덤, 레이드 시작 시 마스터가 일괄 스폰.
 
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 마스터가 PhotonNetwork.InstantiateRoomObject로 생성 **추천** | 방 소유 오브젝트라 생성한 사람과 무관하게 남음. 생성 정보가 서버에 보관되어 중도 참가자도 자동으로 받음 (2주차 플레이어와 같은 원리) | Resources 프리팹 필요 |
| B. 씬에 미리 배치(씬 PhotonView) 후 마스터가 종류만 정해 알림 | 생성 비용 없음 | "지점별 종류 랜덤"을 하려면 두 종류를 다 배치하고 켜고 끄는 처리가 필요 |
 
- 확인 필요: PUN 2의 방 오브젝트 생성 함수 이름은 `InstantiateRoomObject`로 알고 있다(예전 이름 InstantiateSceneObject). 구현할 때 확인
- 사망한 적은 PhotonNetwork.Destroy로 지우지 않고 시체로 남긴다(E10). 보관된 생성 정보는 그대로 두고 상태로 사망을 알린다

| A. 열거형 + switch 한 클래스 | 파일이 적음 | 상태가 늘면 한 클래스가 커지고 상태별 코드가 섞임 |
| B. 상태 클래스 패턴 (IEnemyState: Enter, Tick, Exit + EnemyStateMachine) **추천** | 상태마다 파일이 나뉘어 읽기 쉬움. 구현이 여러 개라 인터페이스 사용 기준에 맞음. 면접에서 설명하기 좋음 | 파일 수 증가 |
 
- B 추천 세부: 공통 상태(순찰, 경계, 추적, 복귀)는 두 종류가 공유하고, 공격 상태만 종류별(돌진 공격, 점사 공격)로 둔다. 상태 번호는 `Enum.cs`의 `EnemyState`로 정의해 동기화에 쓴다
### E6. 소음 전달 방식 [확정: A. 마스터가 동기화 정보로 생성]
 
소음: 달리기, 사격, 회피(근접 공격은 5주차) 시 반경 안의 적에게 전달, 걷기는 아주 작은 반경.
 
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 마스터가 이미 동기화된 정보로 소음을 만듦 **추천** | 새 RPC 없음. 마스터는 남의 캐릭터의 애니메이션 상태(달리기, 회피 횟수)와 발사 RPC를 이미 받고 있음 | 소음 시점이 동기화 지연만큼 늦음 (AI 반응이라 문제없음) |
| B. 각 클라이언트가 소음 RPC를 보냄 | 시점이 정확함 | 메시지 증가, 보내는 코드가 플레이어 쪽에 추가됨 |
 
- A 추천 세부: 소음 발생은 정적 유틸리티 `NoiseSystem.Emit(위치, 반경)`(상태 없는 함수, 싱글톤 아님)이 Physics.OverlapSphere로 Enemy 레이어를 찾아 소음 수신 인터페이스를 호출한다. 마스터에서만 호출된다
### E7. 피격자 최종 확인의 무적 판단 시점 [확정: C. 받은 순간 + 여유 시간]
 
GameDesign 9-1: 마스터가 피격 신호 → 피격자가 자기 화면 기준 무적 여부 확인 → 피격 확정 회신 → 마스터가 체력 감소.
 
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 피격 신호를 받은 순간 무적인지 확인 | 가장 단순 | 무적이 막 끝난 직후 받은 신호는 맞음 처리됨 (지연만큼 불리) |
| B. 신호에 마스터 기준 명중 시각을 넣고, 피격자가 그 시각에 무적이었는지 기록에서 확인 | 가장 정확 | 무적 구간 기록과 시각 비교 코드 필요 |
| C. A + 여유 시간: 지금 무적이거나 무적이 끝난 지 N초 이내면 무적 처리 **추천** | 단순하면서 지연으로 인한 억울함을 줄임 | 여유 시간만큼 무적이 조금 길어짐 (협동 PvE라 허용) |
 
- C 추천 세부: 여유 시간은 인스펙터 값(기본 0.1초). PlayerDodger에 "마지막 무적 종료 시각"을 읽는 프로퍼티 추가가 필요하다
 
### E8. 3주차의 플레이어 체력 0 처리 (임시) [확정: A. 임시 사망 표시 후 회복]
 
다운, 사망은 5주차 이후. 3주차에는 적에게 맞아 체력이 0이 되는 경우를 임시로 처리해야 한다.
 
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 체력 0이면 "사망(임시)" 표시 후 몇 초 뒤 체력 회복 **추천** | 테스트를 끊지 않고 반복할 수 있음 | 5주차에 교체 |
| B. 체력 0에서 멈추고 더 이상 데미지를 받지 않음 | 단순 | 테스트하려면 레이드를 다시 시작해야 함 |
 
- 공통: 플레이어 체력도 마스터 권한이므로 2주차 `NetworkHealth`를 플레이어 프리팹에 재사용한다. 체력 표시는 임시 텍스트(정식 HUD는 7주차)
### E9. 휴면 처리 방식 [확정: A. 일정 간격 거리 검사]
 
GameDesign 5번: 맵 전체 30마리 내외, 플레이어 근처 적만 AI 실행, 먼 적은 AI와 위치 동기화를 멈춤.
 
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 마스터가 일정 간격(예: 0.5초)으로 가장 가까운 플레이어와의 거리를 보고 휴면 전환 **추천** | 단순하고 수치 조정 쉬움. 휴면 중에는 PhotonView 전송도 멈춤 | 매 간격 거리 계산 (30마리 × 4명이라 부담 없음) |
| B. 트리거 영역(플레이어 주변 큰 구)으로 깨우기 | 이벤트 방식 | 플레이어 수만큼 트리거, 경계에서 들락날락 처리 필요 |
 
- A 추천 세부: 깨우는 거리와 재우는 거리를 다르게 둔다(예: 25m 안이면 깨움, 30m 밖이면 휴면). 경계에서 깜빡이는 것을 막기 위함. 추적 중인 적은 휴면하지 않는다
- 확인 필요: 휴면 중 PhotonView 전송을 멈추는 방법(Synchronization을 Off로 바꾸기 또는 OnPhotonSerializeView에서 보내지 않기). 구현할 때 확인
### E10. 적 사망 처리 [확정: A. 시체로 남김]
 
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 시체로 남김: AI·이동·콜라이더(탄 판정) 끄고, 쓰러진 모습으로 둠 **추천** | 4주차 "적 시체가 루팅 상자" 그대로 이어짐 | 시체가 쌓임 (맵당 30마리라 문제없음) |

## 5. 3주차 코드 원칙
 
1. **AI는 마스터에서만 실행한다.** 마스터가 아닌 클라이언트는 받은 값으로 보여 주기만 한다. 분기는 EnemyNetworkSetup 한 곳에서 한다
2. **2주차 구조를 재사용한다.** NetworkHealth, IHitHandler, 발사 RPC 방식, 데이터베이스 + int ID를 적에게도 그대로 쓴다. 새로 만들기 전에 재사용할 수 있는지 먼저 본다
3. **상태 번호 하나로 동기화한다.** 다른 화면에 보여 줄 것은 상태(byte)와 경계 게이지(byte)로 줄인다
4. **수치는 EnemyData와 밸런스 설정에 둔다.** 시야, 게이지, 공격, 배율 값을 코드에 박지 않는다
5. **디버그 표시를 처음부터 만든다.** 시야 Gizmo, 머리 위 상태와 게이지 표시는 AI 조정의 기본 도구다
6. **중도 참가를 기본으로 생각한다.** 적의 모든 상태는 늦게 온 사람도 알 수 있어야 한다
